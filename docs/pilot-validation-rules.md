# Pilot validation rules: inventory, negative corpus and oracle (gate G5)

This is preparation for gate G5's diagnostic comparison, not a qualification
claim. Intersect implements none of these rules yet: its frozen validator
checks structure only (`LoadPhase::Validate` violations), and on the library
and the 157 example models the Pilot reports no diagnostics, so those runs had
nothing to compare. This document lists every validation rule the Pilot
reports, groups the rules into implementation batches, and records a negative
corpus on which the Pilot reports 356 validator diagnostics from 104 issue
codes, with the tools to compare Intersect against it.

Everything was read from, and run with, the Pilot at commit
`692170b71867353b8f90341e61556f49a5beb0e5` (release 2026-08, the commit
`fixtures/native-pilot/v1/manifest.json` pins), with the runtime
`jupyter-sysml-kernel-0.62.0-all.jar` and Java 21.0.6, as in
[tools/pilot-oracle/README.md](../tools/pilot-oracle/README.md). Java is used
only as this verification oracle.

| Artifact | What it is |
|---|---|
| [`tools/pilot-oracle/validation-rules.json`](../tools/pilot-oracle/validation-rules.json) | The rule inventory (machine-readable), generated by `validation_rules.py` from the hand-written inventory, with codes and messages resolved from the Pilot sources |
| `tools/pilot-oracle/validation_rules.py` | The inventory, its cross-check against the sources, and the Markdown tables below |
| `tools/pilot-oracle/validation_corpus.py` | Builds the negative corpus and its expectations from the Pilot's Xpect tests |
| `tools/pilot-oracle/ExampleRun.java` | Pilot runner (now also the target's resource, fragment and node span, and an optional object export) |
| `tools/pilot-oracle/compare_diagnostics.py` | Pilot against Xpect expectations; per-rule counts; Pilot against Intersect |
| `tools/pilot-oracle/test_compare_diagnostics.py` | Inline fixtures for the above (no JVM) |

## The rules

The Pilot validates with two Xtext declarative validators:
`KerMLValidator.xtend` (42 `@Check` methods) and `SysMLValidator.xtend`
(71 `@Check` methods; it extends `KerMLValidator`, so SysML resources get the
KerML rules too, and it overrides `checkDataType`, `checkClass` and
`checkOperatorExpression`). Xtext runs only the validator of the resource's
own language. EMF's `EObjectValidator` (multiplicity and proxy checks) is
switched off in both runtime modules (`USE_EOBJECT_VALIDATOR = false`), and
`KerMLExpressionsValidator` has no checks. The other diagnostics a user sees are
Xtext's own: syntax errors (`org.eclipse.xtext.diagnostics.Diagnostic.Syntax`)
and unresolved references
(`org.eclipse.xtext.diagnostics.Diagnostic.Linking`, "Couldn't resolve
reference to *Kind* '*name*'."). Those are not validation rules and Intersect
already reports its own equivalents in the parse and link phases.

A rule here is one issue a `@Check` method can report: one code, its message
variants, its target and condition. Some methods report several rules
(`checkFeature` has 17).

| | KerML | SysML | Total |
|---|--:|--:|--:|
| Rules | 101 | 108 (3 overrides) | **209** |
| Errors | 91 | 106 | 197 |
| Warnings | 10 | 2 | 12 |
| `@Check` methods | 42 | 71 (5 empty) | 113 |

By what a rule needs (the strongest need decides):

| Category | Rules | Needs |
|---|--:|---|
| Purely structural | 105 | owned relationships, stored attributes and construction defaults, metaclass of resolved targets, owner navigation |
| Derived properties | 97 | derived properties (featuring types, all types, multiplicity, ends, inputs, inherited memberships, `specializes`), implicit relationships, library lookups, static expression result types |
| Name resolution | 2 | member names and inherited memberships (distinguishability); the relative namespace of a feature chain |
| Expression evaluation | 5 | model-level evaluability or evaluated values (multiplicity bounds, metadata values, element filters, end multiplicity 1..1) |

Need tags over all rules (a rule has several): owned 111, derived 90,
implicit 71, defaults 28, library 15, typing 10, evaluation 5, names 2,
resource 1. "typing" (the static result type of an expression: Boolean,
Integer, DurationValue, TimeInstantValue, TensorMeasurementReference) is
counted under derived properties, but the rules that use it are batched with
evaluation (B6) because both need the expression machinery.

### Implementation batches

| Batch | Scope | Rules | Category | Corpus diagnostics | Rules whose code the corpus reports |
|---|---|--:|---|--:|--:|
| B1 | KerML structure: owned relationships, flags and metaclass of resolved targets | 55 | structural (53), derived (2: constructed results) | 35 | 27 |
| B2 | SysML structure: memberships, owning types, variations, referential flags, reference subsettings | 56 | structural (52), derived (4: constructed elements, inherited inputs) | 33 | 21 |
| B3 | Effective typing: "must be typed by" rules over all types of a feature (`getAllTypesOf`) | 29 | derived | 94 | 23 |
| B4 | Derived feature semantics: featuring types, multiplicities, ends, cross features, redefinition/subsetting conformance, connectors, inherited parameters and memberships, library specialization | 55 | derived (54), names (1) | 75 | 34 |
| B5 | Names: namespace distinguishability | 1 | names | 97 | 1 |
| B6 | Expression typing and evaluation: Boolean/Integer/Duration/Time results, model-level evaluability, cast and binding type conformance, implicit binding connectors | 13 | derived/typing (8), evaluation (5) | 22 | 6 |

Suggested order: B1 and B2 first (only stored and constructed facts, 111 rules,
68 corpus diagnostics); then B3, which needs one shared derived property
(all types of a feature, including types inherited through subsetting,
redefinition, conjugated port typing and implicit library defaults) and covers
94 diagnostics with 29 rules; then B5, one rule with the most diagnostics (97,
mostly inherited `self`, `start`, `done`, `that` through implicit library
supertypes), which needs inherited memberships with their names; then B4; B6
last, after expression typing and evaluation exist.

### Pilot quirks to reproduce (or record as deviations)

Codes and messages are recorded verbatim, including:

- Messages used as codes: "At most one individual definition is allowed.",
  "Must be a portion.", "Must be owned by an occurrence definition or usage.",
  "A send action must have a payload.", "A parallel state cannot have
  successions or transitions." (transitions and successions), and the code
  "Invalid Constraint Usage - invalid type".
- Codes used as messages: `validateFeatureReferenceExpressionResult` and
  `validateInstantiationExpressionResult` report their code as the message.
- Swapped or borrowed codes: a `ReferenceUsage` that is not referential gets
  `validateAttributeUsageIsReferential` and "An attribute usage must be
  referential."; an attribute usage gets `validateReferenceUsageIsReference`
  with the same message; an `Expose` outside a view gets
  `validateVariationMembershipOwningNamespace` and "A variant must be an owned
  member of a variation."; `checkFunction` reports
  `validateExpressionResultExpressionMembership`;
  `validateConjugatedPortDefinitionConjugatedPortDefinition` is used for both
  conjugated-port-definition rules.
- Misspelled codes: `validateEndFeatureMembershpIsEnd`,
  `validateNamespaceDistinguishablity`,
  `validateStateSubactionMembershioOwningType`,
  `validateViewDefinitionOnlyOnvViewRendering`,
  `validateVariationMembershipOwningNamespace`,
  `validateMetadataFeatureMetadata`, `invalidateMetadataFeatureBody`.
- Targets: `validateResultExpressionMembershipOwningType` passes
  `ParameterMembership.ownedMemberParameter`, which is not a feature of a
  `ResultExpressionMembership`; three rules report on the object under
  validation with a feature only (`validateOccurrenceUsageIndividualUsage`,
  `validateAttributeUsageEnumerationType_`,
  `validateRequirementVerificationMembershipOwningType`).
- Unguarded nulls: `validateSubsettingConstantConformance` and
  `validateFeatureValueIsInitial` dereference without a null check, so an
  unresolved target makes the check throw inside the Pilot (Xtext logs and
  drops it) instead of reporting.
- Literal-only checks: the multiplicity conformance warnings compare only
  `LiteralInteger` and `LiteralInfinity` bounds.
- 26 declared codes are never reported (the control-node succession rules,
  `validatePartUsageType_`, `validateItemUsageType_`,
  `validateFeatureEndIsConstant`, `validateSubsettingPortionConformance`, ...;
  listed in the JSON as `declared_codes_never_reported`). Five rules are
  unreachable from text because the Pilot's defaults satisfy them
  (`validateEnumerationDefinitionIsVariation`, `validateExposeIsImportAll`,
  `validateFramedConcernMembershipConstraintKind`,
  `validateElementIsImpliedIncluded`, and the conjugated port definition count
  while that definition is constructed).

## Negative corpus

The Pilot repository's Xpect tests (`org.omg.kerml.xpect.tests`,
`org.omg.sysml.xpect.tests`) annotate expected issues in the source:
`// XPECT errors --> "message" at "text"` or a `//* XPECT warnings --- ... ---
*/` block of `"message" at "text"` lines, applying to the text after the
comment. `validation_corpus.py` takes every `.xt` file with an `errors` or
`warnings` expectation, plus every SysML `validation/valid` file, copies it
byte for byte without the `.xt` suffix into its own unit folder with the
non-library files its `XPECT_SETUP` loads, and records each expectation with
the offset of its `at` text (Xpect ignores whitespace in `at`). Units load on
top of the whole pinned library rather than the few library files an Xpect
setup names.

| | Count |
|---|--:|
| Units (one Xpect test file each) | 179 (98 KerML, 81 SysML) |
| Files | 242 (63 support files) |
| Valid controls (SysML `validation/valid`) | 34 (33 without expectations) |
| Expectations | 624: 511 errors, 113 warnings |
| of which syntax or linking (Xtext, not validator) | 262 |

The corpus is generated under `target/pilot-oracle/validation-corpus/` and not
committed (the Pilot test files stay in the sparse checkout).

## Comparing Intersect

`compare_diagnostics.py intersect PILOT.json INTERSECT.json CORPUS [--dump
DUMP.json]` reads Intersect's diagnostics in this format (one list per
resource; resource names are the corpus paths the Pilot report uses):

```json
{"format": "intersect-diagnostics/1",
 "producer": "pilot_examples --validation-corpus ...",
 "resources": {
   "units/025/Feature_invalid_noType.kerml": [
     {"severity": "error", "code": "validateFeatureHasType_",
      "message": "Features must have at least one type", "phase": "validate",
      "element": {"id": "units/025/Feature_invalid_noType.kerml#12", "class": "Feature"},
      "start": 512, "end": 522}]}}
```

It matches by resource, severity, code (the message only when a side has no
code) and target element, as a multiset (`compare.compare_diagnostics`). With
`--dump` (Intersect's linked model of the same files, the export `compare.py`
reads) targets are paired through `compare.py`'s containment pairing against
the Pilot's object export; otherwise by the line and column of the target
element's start (the Pilot's UTF-16 offsets and Intersect's byte offsets both
converted through the source). The report counts `agree`, `pilot_only` and
`intersect_only` per code.

Proposed additions to `intersect_kerml::frozen_load::LoadDiagnostic` (today
`phase`, `message`, `resource`, `object`, `start`, `end`; not changed here):

| Field | Type | Meaning |
|---|---|---|
| `code` | `Option<String>` | The Pilot issue code, verbatim (including the quirks above), for rules ported from the Pilot; the `Violation` variant name for structural violations; none for parse and link problems |
| `severity` | `Severity { Error, Warning, Info }` | Pilot severity; all present diagnostics are errors |
| `rule` (optional) | `Option<String>` | The inventory id, e.g. `KerML.checkFeature.INVALID_FEATURE_HAS_TYPE`, when several rules share a code (9 codes are shared) |
| `feature` (optional) | `Option<String>` | The structural feature the Pilot attaches (e.g. `redefinedFeature`), so a host can narrow the span as the Pilot's issue offset does |

`object` stays the element identity (the target), and `start`/`end` its node
span in bytes. A `LoadDiagnostic` serialized with these fields is one entry of
the format above once grouped by `resource`.

## Batch B2 status (2026-11-08)

All 56 B2 rules are written as `bind validate` rules in
`crates/intersect-kerml/semantics/sysml-validation.rcore` (31 bindings), with
the Pilot's codes, severities and messages verbatim and the inventory id as
`rule`. Each rule binds to the class of the element the Pilot reports on and
reads owners and owned features from containment, the way the Pilot derives
them (`Feature_owningType`, `Type.ownedFeature`,
`FeatureUtil.getBasicFeatureOf`, `AssignmentActionUsage_referent`,
`UsageUtil.getArgumentOf`, `UsageUtil.isLegalVerification`). The
assignment's time-varying check needs `Usage.isVariable` (`mayTimeVary`),
which repeats `sysml-construction.rcore`'s private `may_time_vary` over the
exported name-resolution helpers (the construction package exports none).

| Evidence | Pilot | Intersect agrees | Pilot only | Intersect only |
|---|--:|--:|--:|--:|
| Negative corpus, B2 codes (`compare_diagnostics.py intersect`, line and column) | 33 | 33 | 0 | 0 |
| `fixtures/validation-rules/units/sysml-*`, B2 codes (Pilot run on the same files) | 10 | 10 | 0 | 0 |
| Pilot examples (157 files, 37 folders) and library | 0 | 0 diagnostics, 37 of 37 clean, 8,583 of 8,583 references | | |

The new negative tests (each with non-firing controls in the same file) are
`sysml-assignment-action-usage-referent`, `sysml-send-action-usage-receiver`
(name, qualified name and chain), `sysml-transition-usage-succession` and
`sysml-assert-satisfy-reference` (assert, satisfy, and satisfy reported by both
rules); the Pilot also reports B3 and B5 diagnostics on two of them, which are
not B2's.

Of the 35 B2 rules without a corpus diagnostic, 5 are now verified by those
tests. The other 30 cannot be reached from text, for one of three reasons
(checked with the Pilot where the notation might allow it):

- The notation cannot write the violation (the Pilot reports syntax errors):
  control nodes outside actions; actor, subject and stakeholder members
  outside requirements and cases; objectives outside cases; view renderings
  outside views; entry, do and exit actions outside states; trigger and
  effect memberships outside transitions or of the wrong kind; `require ref`;
  a for loop without its variable; framed concern and verification kinds
  (set by the grammar); requirement constraint memberships outside
  requirements.
- Construction defaults satisfy them, in the Pilot and in Intersect alike:
  composite reference, attribute, event occurrence, perform, exhibit, include
  and port usages, composite features of attribute definitions and usages,
  non-abstract variations, enumeration definitions that are not variations,
  portion kinds without `isPortion`, non-composite objectives and requirement
  constraints, and a port definition without exactly one conjugated port
  definition (or a conjugated one with one).
- Pilot code that cannot fire: `A send action must have a payload.` tests
  whether a list (`TypeUtil.getFeatureMembershipOf`) is a membership; the
  conjugated port definition's original-port-definition rule compares a value
  with itself (`ConjugatedPortDefinition_originalPortDefinition` reads the
  same conjugator); `validateExposeIsImportAll` reads `isImportAll`, which the
  Pilot's expose classes set to true. These three have no check (Intersect
  stores the parsed `false` for `isImportAll` on an expose, which name
  resolution already treats as importing all, so reading the stored value
  would report every expose).

The rules of the second and third groups are implemented with the same
conditions, so they agree with the Pilot by construction; they have no
negative test.

## Batch B3 (SysML) status (2026-11-08)

The 25 SysML rules of B3 (the 4 KerML rules of the batch are not part of
this) are one `bind validate k.Usage` binding in
`crates/intersect-kerml/semantics/sysml-validation.rcore`
(`usage_type_rules`): it computes the usage's types once and applies every
`checkAllTypes` and `checkOneType` rule of the usage's class, with the
Pilot's codes (including `Invalid Constraint Usage - invalid type` and the
message used as the code of "At most one individual definition is
allowed."), messages and exclusions (`checkUsage` skips attribute and
occurrence usages, `checkOccurrenceUsage` port, connection and metadata
usages and steps, and so on), the inventory id as `rule` and the Pilot's
`ref` feature as `feature` (`definition`, `occurrenceDefinition`, ...).

The types are `FeatureUtil.getAllTypesOf` (`FeatureAdapter.getAllTypes`)
rebuilt in Rcore (`all_types`): the types of the owned typings (a
conjugated port typing contributes its conjugated port definition, a typing
written as a chain the chain) of the usage and of every typing feature,
transitively (`Feature.typingFeatures`: owned subsettings, redefinitions and
reference subsettings, not cross subsettings, with their target chains; the
last chaining feature), plus these implicit generalizations: the
metaclass's library default subsetting (`implicit.library_default`), a
variant's typing by its variation definition or subsetting of its variation
usage (`UsageAdapter.addVariationTyping`), and the bound-value subsetting of
a feature valued by a feature reference expression (`enum color1 =
ColorKind::blue;` is typed by `ColorKind`). Types another of them
specializes are then removed (`removeRedundantTypes`), with the
specialization closure the B2 rules already use (`supertypes_of`). The
library default is always taken: the Pilot drops it only when an owned
general specializes it, and that general then has its types, so the result
is the same. Nothing was exported from the construction or resolution
packages (only the already exported `resolution.library`,
`resolution.elements_of` and `implicit.library_default` are used).

| Evidence | Pilot | Intersect agrees | Pilot only | Intersect only |
|---|--:|--:|--:|--:|
| Negative corpus, B3 SysML codes (line and column) | 85 | 85 | 0 | 0 (was 2) |
| Negative corpus, B2 codes | 33 | 33 | 0 | 0 |
| `fixtures/validation-rules/units/sysml-*`, B3 SysML codes | 19 | 19 | 0 | 0 |
| `fixtures/validation-rules/units/sysml-*`, B2 codes | 10 | 10 | 0 | 0 |
| Pilot examples (157 files, 37 folders) and library | 0 | 0 diagnostics, 37 of 37 clean, 8,583 of 8,583 references | | |

The two Intersect-only diagnostics (`validateUsageType_` on `return r1 : T;`
and `return r2 : T;` in `calc c2 : C` of `CalculationUsage_Invalid2.sysml`)
come from name resolution, not from the rule: `C` declares `return T;`, a
result parameter named `T`, and Intersect resolves `T` in `c2` to that
inherited feature, so the result parameters are typed by a feature. The
Pilot hides the inherited `C::T`, which `c2`'s own result parameters
implicitly redefine, and resolves `T` to the attribute definition
`Test::T`. Fixed in name resolution (members hidden by computed
redefinitions, see [examples oracle](pilot-examples-oracle.md)): both
diagnostics are gone, and nothing was added.

New negative tests (Pilot run on the same files, each with non-firing
controls: one definition, the library default, a redundant general, a
subsetted usage): `sysml-verification-case-usage-type`,
`sysml-rendering-usage-type`, `sysml-viewpoint-usage-type` (a viewpoint is
also checked as a requirement, so a requirement definition type fails the
viewpoint rule and, with the default `ViewpointCheck`, the requirement rule
too), `sysml-view-usage-type` and `sysml-metadata-usage-type` (a KerML
metaclass such as `KerML::Feature` does not specialize
`Metadata::MetadataItem`, so the usage has two types; a SysML metaclass
such as `SysML::PartUsage` does). These cover the five B3 SysML rules
without a corpus diagnostic; all 25 now have Pilot-verified negative
evidence.

Not derived (no corpus, fixture, example or library case needs them; each
would add types, so a model that depends on one can miss a Pilot
diagnostic): computed redefinitions (parameters, ends, subjects, objectives
and results redefining those of a general), the bound-value subsetting of a
feature valued by any other expression (its result type needs expression
typing, B6), owned cross features, and feature conjugation (KerML notation
only). The Pilot's more specific library defaults (subobjects,
suboccurrences, portions, actors, ...) are replaced by the base default,
which subsets a feature of the same or a more general type, so it leaves the
same types after redundant ones are removed.

Cost: the whole check phase (every `bind validate` rule, B2 and B3) takes
3.2 s of the library preparation (141 s on a loaded machine) and 2.4 s in
total over the 37 example folders (98 s of loading; at most 0.56 s in one
folder), measured at the `check_end` marker with a local timing patch to
`pilot_examples` that was not committed.

| Rule | How | Evidence |
|---|---|---|

| `checkFlowDefinition` `validateFlowDefinitionConnectionEnds` | end features, inherited included, on the definition or its third and later owned ends | corpus 2, fixture 1 |
| `checkAcceptActionUsage`, `checkForLoopActionUsage`, `checkIfActionUsage`, `checkWhileLoopActionUsage`, `checkTransitionUsage` parameter counts (5 rules) | owned input parameters (`ActionUsage.inputParameters()` is `UsageUtil.getOwnedInputParametersOf`, not inherited ones, as the inventory says) | by construction: the grammar always writes these parameters |
| `checkTransitionUsage` `validateTransitionUsageTriggerActions` | the transition's source (`UsageUtil.getSourceFeatureOf`, with the previous feature of a target transition, `TransitionUsageAdapter.computeSource`) is not a state | corpus 1, fixture 1 |
| Only one subject (requirement and case definitions and usages, 4 rules), only one objective (case definitions and usages, 2), at most one view rendering (view definitions and usages, 2) | `checkAtMostOneRelationship` over the feature memberships, owned and inherited | corpus 12, fixtures 8 |
| Subject must be first parameter (4 rules) | `checkSubjectParameter`: the first input of the feature memberships | corpus 5, fixtures 3 |

The inherited feature memberships (`TypeUtil.getFeatureMembershipOf`) are
rebuilt locally (`b4_relevant_memberships`), since the name-resolution
package only exports name-based lookups: owned memberships first, then each
general's public and protected owned memberships and its own inherited ones,
without those `TypeAdapter.removeRedefinedFeatures` drops. That needs the
Pilot's computed redefinitions (`FeatureAdapter.addRedefinitions`): an end
redefines the end at its position in each general, a parameter of a
behavior or step the (non-result) parameter at its position, a result the
general's result, and the first owned objective the general's objective.
So `requirement def F { in attribute x; }` reports "Subject must be first
parameter." (x redefines `RequirementCheck::subj`), and `case def P :> L, M
{ objective p1; }` has one objective. Nothing was exported from the
construction or resolution packages.

Approximations (no corpus, fixture, example or library case depends on
them): only subject, objective and view rendering memberships, directed
features and ends are walked, so a feature of another kind that redefines
one of them hides it only when the type owns it; a feature with explicit
generals does not also take its library default subsetting (the Pilot adds
it when there is no owned subsetting; its subject and objective are then
redefined through the explicit general's); directions are the stored ones
(`Type.directionOf`'s conjugation is not applied); state and transition
subaction redefinitions are not computed; an inherited flow definition end
after the second, which the Pilot would report on the inherited feature, is
not reported.

Two derivations the inventory's summaries do not mention turned out to
matter on the corpus and the examples: the library default general is
taken even when a type has explicit generals (`case c2 : A;`, typed by a
part definition, still inherits `Cases::Case::subj` through
`Cases::cases`, so its first input is a subject), and every view
rendering also redefines `Views::View::viewRendering`
(`RenderingUsageAdapter.addRedefinitions`), so an owned view rendering
hides the inherited ones (`view v : V { render r; }` in the Simple Tests
example `ViewTest.sysml` is valid).

How the derived properties are read (each rule's comment names the Pilot
code it follows):

- Featuring types (`Feature_featuringType`, `FeatureAdapter.computeFeaturingType`):
  owned type featurings, the owning type, or for a variable feature the
  snapshots feature of the owning type (kept as "the snapshots of T"), and
  the first chaining feature's. They are taken as known only for features of
  the loaded resources with an owning type, owned by a non-type namespace
  (not a connector or expression), or chains owned by a relationship;
  otherwise (library features, which the Pilot transforms on demand;
  variants, cross features, feature value expressions) the feature counts as
  featured within anything. `isFeaturedWithin`, `TypeUtil.isCompatible`
  (two features without owned features are compatible) and
  `FeatureUtil.canAccess` follow the Pilot over these, with the snapshots
  feature of T compatible with what the library snapshots feature
  specializes.
- Specialization for featuring (`conforms`) uses the name resolution's
  generals (with library defaults), conjugation originals and computed
  redefinitions, and treats as conforming to anything a type whose implicit
  generals are not modelled: an expression; a feature with a bound value or
  a parameter, without owned specializations (bound-value and payload
  subsettings); a type with prefix metadata on it or a supertype (semantic
  metadata base types). This keeps the Arrowhead and Simple Tests examples,
  unit 174 and the transition payload chain in `StateTest.sysml` clean.
- `Type::directionOf`: a breadth-first walk from the featuring type to the
  redefined feature's owning type through generals, flipping through each
  conjugation; a walk that reaches it both ways gives no direction. Only
  directed redefined features of the loaded resources are checked, and not
  a flow end's feature (its direction is set from its redefined feature).
- Multiplicities: the owned multiplicity range, or for the empty
  multiplicity the SysML construction adds as a usage's default
  (`usage_multiplicity`), `Base::exactlyOne` (1..1) outside the library.
  Bounds are compared as literal integers and `*` only, as the Pilot does.
  These two rules are a binding of their own because literal integer values
  are `Int32`; the direct executor runs `Int32` since 2026-11-09 (before, the
  binding ran on the VM).
- Cross features: rules on a feature's owned cross subsetting; a feature
  whose cross feature is an owned cross feature (implicitly typed and
  specializing, `addOwnedCrossFeatureSpecialization`) is not checked.
- `validateClassifierDefaultSupertype_` is checked for conjugated
  classifiers only (a conjugation cycle, or an original that does not
  specialize the default); a specialization cycle of unconjugated types is
  not checked (`classifier B :> B;` is valid in the Pilot).
- Result expressions are counted over owned specializations, conjugations
  and chains (library defaults have none; computed redefinitions are not
  followed). Related features of a connector are its owned ends' reference
  subsettings, counted only without explicit generals and when the end
  features are the owned ends; successions are skipped. Association related
  types are the end features' types (ends of the first general with more
  ends included). Feature value overriding walks all redefined features,
  computed redefinitions included.

- `Feature::isVariable`: the KerML parser makes a constant feature variable;
  a SysML usage is variable when it may vary in time (`UsageImpl.isVariable`

  library generals, not a portion, self link, happens link or composite
  action). The helpers are a copy of sysml-construction's private ones,
  because that source compiles after the KerML validation.
- Specialization ends are read through the stored feature that redefines
  `specific`/`general` (the referencing feature of a reference subsetting and
  the crossing feature of a cross subsetting are the owning feature).
- SysML's checkDataType/checkClass overrides are chosen for definitions (a
  SysML resource has no KerML data types or classes); the KerML bracket
  warning is suppressed for resources whose name ends in `.sysml`.

  library function looked up by operator or kind) is taken as found;
  `validateInvocationExpressionOwnedFeatures`' guard reads a feature's owned
  typings only, not its derived types.

  of the owned typings, then those of the typing features (the original of a
  conjugated feature; otherwise the subsetted features of the owned
  subsettings other than cross subsettings, the computed redefinitions, the
  library default unless an explicit general specializes it, and the last
  chaining feature), each feature visited once along a path; then
  removeRedundantTypes (from the last, a type that another type
  specializes is removed). Implicit typings (expression results, variants,
  owned cross features) are not added. The library defaults and computed
  redefinitions are those of B5 below.

  typing, the original feature's types for a conjugated feature, or for any
  other feature its library default (with the library loaded every

#### B5 status in Intersect (2026-11-09)

`validateNamespaceDistinguishablity` is in the `k.Element` binding of
`crates/intersect-kerml/semantics/kerml-validation.rcore`
(`distinguishability`, beside the B1 element rule), so that every issue is
on the Pilot's target: an element owned by an owning membership is checked
as that membership's member (feature `declaredShortName` or
`declaredName`), a membership that is not an owning membership as an alias
(`memberShortName` or `memberName`), and a type for its inherited
memberships among themselves (no feature). Messages are built as the
Pilot's `identifyDuplicates`: the owning namespaces of the duplicates other
than the checked one, by effective name ("" when unnamed), sorted in Java
String order (compared on the hexadecimal of the UTF-8 bytes, since Rcore
has no string ordering), escaped as names (quoted unless an identifier) and
joined with ", "; the duplicated name is the stored one (names are stored
with their escapes as written, which is what `escapeString` gives back).

The name resolution's helpers are name-keyed lookups (`inherited(ns, name)`)
and none is exported, so the sets this rule needs are computed in the
validation source, following the Pilot rather than the resolution's
approximations:

- Membership names: an owning membership's are its element's effective
  name and short name (FeatureUtil.computeEffectiveName: the declared name
  when a name or short name is declared, otherwise the naming feature's;
  the naming feature is the variant's referenced feature, the performed
  action, exhibited state or included use case, a required constraint's
  referenced constraint, a view rendering's referenced feature, a
  transition payload parameter's trigger payload, otherwise the first owned
  or computed redefined feature; a conjugated port definition is `~` and its
  port definition's name); another membership's are its stored
  `memberName` and `memberShortName`.
- Computed redefinitions (FeatureAdapter.getRedefinedFeaturesWithComputed):
  a result parameter redefines each general's result parameter, another
  parameter of a behavior or step the general's parameter at its position,
  an end the general's end at its position, a case objective each case
  general's objective, a transition's trigger and effect actions
  `TransitionAction::accepter` and `effect`; the generals are the owned
  specializations' generals, the original type, the binary default and the
  library defaults below, a feature chain read through its last chaining
  feature (`step :> monitor.startObservation { in observer ...; }`).
- Inherited memberships (TypeAdapter.getInheritedMemberships): the union of
  each general's non-private memberships (owned public and protected ones,
  those its public and protected imports import, and its own inherited
  memberships), then without the memberships of features that the type's
  owned features redefine (directly or through their redefined features)
  and of features another inherited membership's feature redefines
  (removeRedefinedFeatures). Memoised per type (the direct executor keeps
  pure call results for the whole check phase).
- Generals (TypeUtil.getGeneralTypesOf with the implicit generals): a
  conjugated type's original type and owned specializations; otherwise the
  owned specializations' generals (cross subsettings included), the binary
  default, the computed redefinitions and the library defaults that none of
  these specializes without passing through the type itself
  (removeUnnecessaryImplicitGeneralTypes, specializesExcludingTarget); and a
  chain's last chaining feature.
- Library defaults: the metaclass's base default, except that a connector
  with two owned ends takes its "binary" default (`Links::binaryLinks`,
  `Links::selfLinks`, `Interfaces::binaryInterfaces`, ...); an occurrence
  usage also takes `Base::dataValues` when typed by a data type and
  `Objects::objects` when typed by a structure; another feature whose base
  default is `Base::things` (or an attribute usage's `Base::dataValues`)
  takes the default of its owned types' kind (`Objects::objects`,
  `Occurrences::occurrences`, `Base::dataValues`), so `attribute a : A`
  with A a part definition inherits `Object::self`, which `Part::self`
  redefines, and has no clash, while `attribute b : A::a` does.
- Specialization cycles are walked without revisiting a type (the Pilot's
  excludedTypes): outside the library any cycle through non-library
  generals, in the library features that specialize siblings
  (`SelfLink::thisThing` and `sameThing`).

Approximations (the results below are with them): the composite variants of the defaults
(`subobjects`, `suboccurrences`, `portions`) and the more specific implicit
subsettings (subitems, subparts, subactions, enacted and owned
performances, state subactions' `entryAction` ...) are not added (the Pilot
drops such a default when another general's own implicit subsetting
specializes it, so adding them without those gives clashes the Pilot does
not have, e.g. `part :>> producer :> producer_2;` inheriting both
`producer_2::incomingTransferSort` and `suboccurrences`'s); semantic
metadata base types and implicit typings are not generals; imports are
followed without recursive imports and filter conditions; a cycle through
an import and a specialization is not guarded; computed redefinitions of a
parameter with owned redefinitions are kept (the Pilot drops those equal to
an owned target, which only removes duplicates).
